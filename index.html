Health Data SQL Agent

Ask a question in plain English and get an answer, the SQL behind it, the data and a chart. A Databricks-hosted model writes the query; guardrails make sure it is read-only and only touches the Gold layer.

-- "What is the 30-day readmission rate for each payer type?"
SELECT py.payer_type,
       ROUND(AVG(CASE WHEN f.has_readmission_30d THEN 1.0 ELSE 0 END), 4) AS readmission_rate
FROM workspace.gold.fact_encounter f
JOIN workspace.gold.dim_payer py ON f.payer_id = py.payer_id
WHERE f.is_readmission_eligible
GROUP BY py.payer_type
  • Schema context is read live from table and column comments, so documentation and agent stay in sync.
  • Self-corrects: query errors go back to the model for a fix, up to three attempts.

Building a healthcare lakehouse on Databricks Free Edition

Priyanka Andrew Charan · Databricks · 5 min read

I wanted a portfolio project that looks like the work I do every day: messy clinical data, strict privacy, and stakeholders who need one trustworthy number. Real patient data was out of the question, so I generated it. Synthea simulates full medical histories, and with a fixed seed it gave me 57,398 patients in Massachusetts, 50,000 of them living, with encounters, conditions, medications and claims.

Raw files first, untouched

The CSVs landed in an S3 bucket and stayed there unchanged. Bronze in Databricks is a straight copy into Delta tables with two audit columns: which file a row came from and when it arrived. If anything downstream looks wrong, I can always trace it back.

Silver is where the real work happens

Letting Spark infer the schema is convenient, and it quietly broke three things:

  • ZIP codes became numbers, so 02139 turned into 2139. Every Boston-area ZIP lost its leading zero.
  • Clinical codes such as SNOMED and RxNorm became integers, which is wrong for an identifier and risky for joins.
  • Money arrived as floating point, which is not what you want in a cost report.

Silver casts every column explicitly, restores the ZIP and FIPS codes, stores money as decimals and standardises labels. It also drops SSNs, names and street addresses, so nothing past Bronze carries direct identifiers. Fourteen data quality checks run on every load (unique keys, orphan records, negative costs, impossible dates), and a failure stops the pipeline before Gold is rebuilt.

Gold is designed for questions

Gold is a star schema: patients, providers, organizations, payers and dates around encounter, condition and medication facts. The definitions are where the value is. A 30-day readmission rate, for example, should only count stays whose 30-day window is complete, otherwise the most recent month always looks artificially good. I put that rule in a column, wrote it into the column comment, and added primary and foreign keys so both the dashboard and an AI agent can find the right joins.

Shipping it like production

The notebooks, the job and the dashboard are one Databricks Asset Bundle. Every push to GitHub runs the checks and deploys automatically. On top of Gold I built a text-to-SQL agent that answers plain-English questions, with guardrails that keep it read-only and away from anything but the Gold layer.

The code is on GitHub.

Fixing truncated text in Tableau when connecting to Databricks

Priyanka Andrew Charan · Tableau + Databricks · 4 min read

The problem

When Tableau connects to Databricks, long text fields may get cut to 255 characters because of how the ODBC driver defines them. This post explains why that happens and a simple way to fix it so you can see the full data.

Why this happens

Tableau depends on the ODBC driver to understand the structure of the data. If the driver says a column is limited to 255 characters, Tableau will not retrieve anything beyond that, leading to truncated values in your dashboards. In the example below the column is limited to 255 characters, so the text appears cut off mid-sentence.

The workaround

Tableau provides a way to override such limitations using .tdc (Tableau Data Customization) files. A .tdc file is an XML-based configuration file that lets you customize how Tableau interacts with a data source. By modifying this file, you can tell Tableau to treat string columns as much larger (for example, up to 32,767 characters) instead of the default 255.

Steps to create a .tdc file for Databricks

1. Locate the Tableau Datasources folder

Find the Datasources folder in your My Tableau Repository. To locate your repository, open Tableau, go to File and select Repository Location.

Copy the repository path shown at the top, then paste it into your File Explorer search bar. This takes you directly to your repository folder.

2. Create the .tdc file

Create a file in Notepad or Visual Studio Code and save it with a .tdc extension:

Databricks.tdc

You can also place .tdc files in Tableau's Drivers folder for a global effect:

  • Windows: C:\Program Files\Tableau\Drivers
  • macOS: /Applications/Tableau Desktop.app/Contents/Drivers

3. Add the XML content

Here is sample code for the .tdc file to increase the string length:

<?xml version='1.0' encoding='utf-8' ?>
<connection-customization class='databricks' enabled='true' version='10.4'>
  <vendor name='databricks'/>
  <driver name='databricks'/>
  <customizations>
    <customization name='odbc-connect-string-extras' value='DefaultStringColumnLength=1024' />
  </customizations>
</connection-customization>

4. Restart Tableau

After saving the .tdc file, restart Tableau Desktop so it loads the new settings.

5. Verify

Connect to Databricks again and check a long string column. It should now show longer values without truncation.

Summary

Truncated text in Tableau when connecting to Databricks can be confusing, especially when the full data exists in the source. The issue comes down to how the ODBC driver reports string lengths, and a simple .tdc customization overrides this limitation so you see your data as intended. Your dashboards then reflect complete and accurate information, without misleading insights caused by cut-off text.

Tableau extract failures with Databricks views

Priyanka Andrew Charan · Tableau + Databricks · 2 min read

Problem

Long-running Tableau extracts from Databricks views fail, while smaller extracts complete successfully.

Cause

The issue is caused by the Query Result Download (Cloud Fetch) feature. It uses temporary cloud storage URLs to download large query result sets. For long-running extracts, these URLs can expire before the download completes, so the extract fails. Smaller extracts succeed because they finish before the URLs expire.

Workaround

Disable Query Result Download by adding a parameter to the Databricks connection in Tableau Desktop:

  1. Open the Databricks connection in Tableau Desktop.
  2. Go to the Advanced tab.
  3. In Extra ODBC options, append ;EnableQueryResultDownload=0. Combined with the string-length fix, the full value is:
DefaultStringColumnLength=1024;EnableQueryResultDownload=0
  1. Sign in again and rerun the extract.

If that does not work, use the same .tdc approach described in Fixing truncated text in Tableau when connecting to Databricks and add the parameter to the .tdc file:

<?xml version='1.0' encoding='utf-8' ?>
<connection-customization class='databricks' enabled='true' version='10.4'>
  <vendor name='databricks'/>
  <driver name='databricks'/>
  <customizations>
    <customization name='odbc-connect-string-extras'
                   value='DefaultStringColumnLength=1024;EnableQueryResultDownload=0' />
  </customizations>
</connection-customization>

Note: this is a workaround. Disabling Cloud Fetch can make very large extracts slower, so revisit it when your driver and Databricks versions change.

Using containers in Tableau

Priyanka Andrew Charan · Tableau · 4 min read

A well-organized dashboard makes data easy to understand and act on, while a cluttered layout hides the insights. This guide builds a clean dashboard layout with containers, so it looks good and stays easy to update later. The example uses Tableau's Superstore sample data.

1. Add and set up the vertical container

Hold down Shift and drag a Vertical Container onto the dashboard. In the Layout pane, set the X and Y positions to 0, 0 so the container starts at the top-left corner.

Set the Width (W) and Height (H) to the size of the dashboard so the container fills the space.

2. Add a blank object to keep alignment

From the Objects section, drag a Blank object into the vertical container. This avoids leftover space at the bottom that throws off the alignment later. Optionally, give it a background color so you can tell it apart.

3. Add the dashboard title

Drag a Text object into the vertical container and place it at the top for the dashboard name.

4. Add the KPI chart

Drag the KPI sheet below the title, inside the vertical container. Notice the Item hierarchy in the dashboard pane: every object sits neatly under the vertical container.

5. Add a horizontal container

Drag a Horizontal Container below the KPI chart.

Add the Profit by Segment and Profit by Category charts side by side inside it.

6. Deal with legends and tile spacing

If the legends look cluttered or don't fit the layout, it's time to clean up.

Remove the Tiled container that appeared at the bottom of the dashboard.

7. Remove the legends and tiled containers

Delete the legends and the unwanted tiled container to keep a clean layout and hierarchy.

8. Finish the layout

Add the last sheet and make sure every component is aligned.

Remove the blank object if needed so everything fits.

9. Keep a clean hierarchy

The key to a maintainable dashboard is a clean hierarchy. Remove any extra tiled objects created by legends or filters.

With this structure you can add or change objects later without disturbing the layout.

Five small Tableau features that save time

Priyanka Andrew Charan · Tableau · 4 min read

Tableau has many small features that save time once you know them. This post covers five: showing column labels for table text, restoring row labels, filtering calculations, adding comments for new users, and formatting text in calculations. The examples use Tableau's Superstore sample data.

1. Show column labels for table text

A common issue: you drag a measure such as Profit to the Text shelf, and the column label for that measure doesn't appear.

To fix it:

  1. Add Measure Names to Columns. Drag Measure Names to the Columns shelf. Then, holding Ctrl, drag it to the Filters shelf as well and select the measure you want (for example, Profit).

  1. Move Measure Values to Text. Drag Measure Values from the Data pane to the Text shelf.

  1. The field label now appears in the table.

2. Restore row labels

Row labels are hidden when Hide Field Labels for Rows is selected, and it isn't obvious how to bring them back.

To restore them, open the Analysis menu, choose Table Layout and select Show Field Labels for Rows.

Tip: if the headers for Measure Names are missing, click Measure Names and select Show Header.

3. Filter to calculations only

In the Data pane, open the dropdown menu, choose Filter By and pick the criteria, such as calculations. Only those fields stay visible, so you can focus on the ones you need.

4. Add comments to describe fields for new users

Comments help new users understand the data without cluttering the workspace.

  1. Right-click a field in the Data pane.
  2. Choose Default Properties, then Comment, and write a description.
  3. The comment appears when anyone hovers over the field.

5. Add a line break inside a text calculation

To put text on a new line in a calculation, add + " then press Enter and close the quote. Pressing Enter inside the quotation marks creates a line break in the output.

The result is easier to read text in the view.

These small techniques make day-to-day work in Tableau smoother for beginners and experienced users alike.

Streamlining data processing with AWS

Priyanka Andrew Charan · AWS · 3 min read

Cloud services make it much easier to automate routine data processing. This post shows a simple pattern I use: a Python script that pulls data from Snowflake, transforms it and writes it back, running on AWS without a server to manage.

Overview

The script runs as an AWS Lambda function, and Amazon CloudWatch (EventBridge) schedules it, so the job runs on time with no manual effort. Three services fit together:

  1. AWS Lambda runs the script.
  2. Amazon EC2 prepares the dependencies.
  3. Amazon CloudWatch handles the schedule.

AWS Lambda: running the script

Lambda runs your code in response to events, with no servers to manage.

  1. Write the code in a language Lambda supports, such as Python, Node.js or Java. Here it is a Python script.
  2. Upload it to Lambda. Think of it as putting your code into a box in the cloud.
  3. Zip and upload the script's dependencies, built in a Linux-compatible environment.
  4. Test and run the function.

The full walkthrough is in How to automate Python scripts using AWS Lambda.

Amazon EC2: building and testing dependencies

Lambda runs on Linux, so any dependency your code uses must be built for Linux, otherwise you get runtime errors when you test the function.

  1. Launch an EC2 instance (a computer that lives in the cloud) with an Amazon Linux 2 AMI.
  2. Install the dependencies on the instance.
  3. Create the deployment package and zip it, then copy it to an S3 bucket or download it with the AWS CLI.

Other ways to build Linux-ready dependencies are covered in Ensuring your dependencies are AWS Lambda ready.

Amazon CloudWatch: scheduling

To run the function on a schedule:

  1. On the Lambda function page, click Add trigger.
  2. Choose EventBridge (CloudWatch Events) as the source.
  3. Create a new rule with a name, description and schedule expression, then click Add.

Summary

  • AWS Lambda runs the script without server management.
  • Amazon EC2 builds and tests dependencies in a Linux environment.
  • Amazon CloudWatch schedules the runs.

Together they make a small, reliable pipeline that removes manual work and leaves more time for analysis.

How to automate Python scripts using AWS Lambda

Priyanka Andrew Charan · AWS · 4 min read

AWS Lambda lets you run Python code without managing servers. You can set Lambda to run in response to specific events, which makes it a good fit for automating tasks like updating data in Snowflake. In this guide I walk through how to set up and test a simple Python script in Lambda.

Step 1: Write your Python script

First, you need a Python script that does the work, whether that is interacting with Snowflake or any other service. Here is an example handler that calls an external API and returns the result. You can modify it to fit your use case, for example to update rows in a Snowflake table.

Step 2: Upload your script to AWS Lambda

Lambda is like a box in the cloud where your code lives and runs when triggered by an event.

  1. Create a new Lambda function. In the AWS Lambda console, create a new function and choose Author from scratch. Give it a relevant name, like snowflake-update-function, pick Python 3.8 or later as the runtime, and give it a basic execution role.
  2. Upload your Python script. Paste the script directly into the editor, or upload it as a .zip file. Use the .zip approach if you have dependencies such as the Snowflake connector.

Step 3: Package your script with dependencies

Lambda doesn't include libraries like snowflake-connector-python, so you need to ship them in a .zip file along with your script.

mkdir my_lambda_package
cd my_lambda_package
pip install snowflake-connector-python -t .
cp ../lambda_snowflake_update.py .
zip -r9 my_lambda_package.zip .

Then, in the Lambda console under Function code, choose Upload a .zip file and upload my_lambda_package.zip. Build the package on Amazon Linux so compiled libraries match the Lambda runtime; see Ensuring your dependencies are AWS Lambda ready.

Step 4: Test your Lambda function

Lambda functions are event-driven, so create a test event to simulate the data your function will process.

  1. In the Lambda console, click Test, select Create new test event and name it, for example TestSnowflakeUpdate.
  2. Use sample JSON like this, replacing the placeholders with values for your table:
{
  "table_name": "your_table_name",
  "column_to_update": "your_column_name",
  "new_value": "new_value_for_column",
  "condition_column": "your_condition_column",
  "condition_value": "value_to_match"
}
  1. Click Test again to run the function. If everything works you should see a success message like:
{
  "statusCode": 200,
  "body": "Successfully updated 1 row(s)."
}
  1. Check the logs. Lambda logs everything to CloudWatch, so you can debug and monitor execution in CloudWatch Logs.

Step 5: Set permissions and monitor execution

  • IAM role permissions. Make sure the role Lambda uses can access every resource it needs. If Snowflake is reached through a VPC, configure the function's VPC settings.
  • Monitoring. CloudWatch shows how often the function runs, how long it takes and any errors.

Summary

  1. Write the script that does what you need, for example update a Snowflake table.
  2. Upload it to Lambda, directly or as a .zip with its dependencies.
  3. Test it with a test event that simulates real input.
  4. Set permissions so the function can reach external resources.
  5. Monitor and iterate with CloudWatch.

Lambda scales automatically and handles the infrastructure, so you can focus on the logic.

Ensuring your dependencies are AWS Lambda ready

Priyanka Andrew Charan · AWS · 3 min read

When you deploy code to AWS Lambda, your dependencies have to be compatible with the Lambda environment, which runs on Amazon Linux. Here is how to get it right.

1. Develop in the right environment

To avoid compatibility issues, build and package your dependencies in an environment that mirrors Lambda's Amazon Linux.

Option A: Docker

  1. Start an Amazon Linux container. This gives you a local environment that matches Lambda.
FROM amazonlinux:2
RUN yum install -y python3-pip
  1. Install your dependencies inside the container.
docker run -it amazonlinux:2 /bin/bash
yum install -y python3-pip
pip3 install --target /lambda/ python-package
  1. Copy the files out of the container.
docker cp <container_id>:/lambda /path/to/your/project
  1. Zip it up with your Lambda function code.

Option B: Amazon EC2

  1. Launch an EC2 instance with an Amazon Linux 2 AMI.
  2. SSH into the instance and install your dependencies:
yum install -y python3-pip
pip3 install --target /lambda/ python-package
  1. Create the deployment package:
zip -r function.zip /lambda/ your_lambda_function.py

2. Use Lambda layers

If several functions use the same libraries, package them once as a layer:

  1. Build the layer. Zip your dependencies with the folder structure python/lib/pythonX.X/site-packages/, where X.X matches your Python version.
  2. Publish the layer. In the Lambda console, create a new layer and upload the zip.
  3. Attach the layer to each function that needs it.

3. Test before you go live

  1. Test locally in Docker or on the EC2 instance, the same environment the code will run in.
  2. Deploy and validate. Watch the logs and metrics after deploying to catch issues early.

Summary

Build in an Amazon Linux environment, share common libraries through layers, and test in the same environment you deploy to. That avoids the most common Lambda packaging errors.
